Personnaliser thèmes, couleurs, polices et touches du terminal

Choisissez les couleurs de la page parmi dix thèmes, donnez à chaque terminal un thème à lui, et réglez des couleurs isolées, la police et le curseur du terminal et chaque touche, dans Settings ou dans un fichier de réglages qui se décrit lui-même.

Dix thèmes de couleurs, clairs et sombres

Settings → Appearance commence par trois choix : Light, Dark et Match the system, qui est le départ d’une nouvelle installation et qui suit le système quand il change. En dessous, vous choisissez un thème de chaque sorte : Light, High contrast light, Solarized light ou Gruvbox light ; Dark, High contrast dark, Solarized dark, Gruvbox dark, Nord ou Dracula. Chacun est montré avec une petite image de ses couleurs.

Un changement s’applique aussitôt à la page et à chaque terminal, sans recharger, et il est gardé dans le fichier de réglages, si bien que chaque navigateur où vous ouvrez Aubergine s’accorde. La palette a la même chose en commandes, par exemple Color theme: Nord.

Un thème de couleurs différent pour chaque terminal

Theme… dans le menu d’un terminal le dessine dans l’un des dix thèmes, quel que soit celui de la page. Seul son corps change : son titre, sa note et ses détails restent comme la page. Un terminal sans thème à lui suit Terminal theme dans Settings, le thème par défaut des terminaux, et à défaut, la page.

Le même choix est dans le menu de la ligne du terminal dans la liste, dans ses détails et dans la palette. Un terminal et un cadre peuvent aussi avoir une couleur à eux, l’une de treize ou Your own… pour n’importe quelle couleur, et l’onglet d’un canevas aussi ; la couleur d’un terminal est aussi celle de sa ligne dans la liste.

Régler des couleurs isolées à la main

Au-delà des thèmes, 35 couleurs de la page se règlent dans le fichier de réglages, config.json, sous appearance.colors : le nom d’une couleur et une valeur écrite #rrggbb. Écrite en haut, une couleur s’applique à tous les thèmes ; écrite sous l’ID d’un thème entre crochets, comme "[nord]", elle s’applique à ce seul thème, et l’emporte.

{
  "$schema": "./config.schema.json",
  "appearance": {
    "colors": {
      "accent": "#c678dd",
      "[nord]": { "terminal-bg": "#242933" }
    }
  }
}

Les noms sont les jetons de couleur de la page, comme bg, text, accent et terminal-bg ; docs/design.md les liste. Une entrée fausse est ignorée, et le reste du fichier compte toujours ; Settings → Appearance dit laquelle. Les couleurs que vous réglez sont les vôtres : rien ne vérifie que ce que vous avez écrit se lit.

Vos propres thèmes, en fichiers

Un thème à vous est un fichier JSON dans themes/ du dossier de données : l’un des dix comme base, du même genre, avec n’importe lesquelles des 35 couleurs par-dessus, et les couleurs propres d’un terminal : son texte, le curseur, ce qui est sélectionné et les seize couleurs qu’un programme demande. Il est listé après les dix de son genre, marqué comme le vôtre, et se choisit partout où eux se choisissent : pour la page, comme défaut des terminaux ou pour un seul terminal. Les ombres et l’anneau de focus restent ceux de la base, et rien dans un fichier n’est exécuté.

{
  "$schema": "../theme.schema.json",
  "name": "Harbor",
  "kind": "dark",
  "base": "nord",
  "colors": { "bg": "#0e1a24", "accent": "#5fb3b3" },
  "terminal": { "foreground": "#d8dee9", "cursor": "#5fb3b3" }
}

aubergine theme new harbor --from nord écrit un fichier de départ, avec chaque couleur du thème d’origine ; aubergine theme check dit ce qui ne va pas dans un fichier ; Read themes again dans Settings prend en compte un changement. C’est à vous de juger si vos couleurs se lisent : Settings dit seulement quand un texte risque d’être difficile à lire. docs/themes.md décrit le format.

Polices, curseur et raccourcis clavier

Terminal text dans Settings → Appearance règle la taille du texte d’un terminal, de 8 à 32 pixels, et sa police, sous forme de liste dont la première police trouvée est utilisée. Cursor règle sa forme, bloc, barre ou soulignement, et s’il clignote.

Chaque touche se change. Ajoutez shortcuts au fichier de réglages : le nom d’une commande avec un raccourci, une liste de raccourcis, ou null pour aucune touche. shortcutsInAppWindow prend la même chose et ne s’applique que là où Aubergine est installé comme app avec sa propre fenêtre. Rechargez la page, et la feuille des raccourcis (?), la palette et les infobulles montrent les touches telles que vous les avez réglées.

{
  "shortcuts": {
    "terminal.park": "X",
    "attention.next": ["Ctrl+Cmd+G", "W"],
    "view.fit": null
  }
}

Une touche réglée deux fois, ou une qui ne se lit pas, est signalée en haut de la feuille des raccourcis et par le serveur, et le reste du fichier s’applique toujours. Une touche seule, ou Ctrl ou Option avec une touche, ne marche que tant qu’aucun terminal n’a le clavier, pour que chaque programme d’un terminal reçoive toujours les touches dont il a besoin. Plus dans Keyboard, dans le README.

Un fichier de réglages qui se décrit lui-même

Tout cela est gardé dans config.json dans le dossier de données d’Aubergine, et aubergine settings path affiche où il est. Chaque clé peut être omise. Un fichier illisible veut dire les valeurs par défaut, jamais un serveur qui ne démarre pas. Settings dans la page n’écrit que les clés qu’il change et laisse le reste du fichier tel que vous l’avez écrit.

À chaque démarrage, le serveur écrit config.schema.json à côté du fichier. Ajoutez une ligne, et un éditeur qui lit JSON Schema décrit et complète chaque clé :

{ "$schema": "./config.schema.json" }

aubergine settings list affiche chaque clé avec sa valeur actuelle, marquée là où ce n’est pas la valeur par défaut, et aubergine settings schema affiche le schéma. docs/settings.md décrit chaque clé, sa valeur par défaut, et si c’est Settings ou vous qui l’écrivez.

aubergine settings path
aubergine settings list
aubergine settings schema

Dans la page, Settings → Every setting liste les mêmes clés avec leurs valeurs, et les trouve pendant que vous tapez. Une clé que Settings change vous mène à son contrôle ; une clé écrite à la main a Copy, pour la ligne à ajouter au fichier. Rien là ne change un réglage.

Certains choix appartiennent à ce navigateur et y sont gardés : si les canevas sont des onglets, une liste ou une colonne ; où se tient la barre au-dessus du canevas et si elle reste ouverte ; si le panneau latéral et la carte sont repliés ; la largeur du panneau et des détails d’un terminal ; et comment la liste des terminaux est filtrée, groupée et triée.

Ce qu’un programme ou un agent peut changer, et ce qui reste à vous

Par l’API locale, un programme muni d’un jeton d’API peut arranger les canevas avec canvases:write : les nommer, les colorer et les ordonner, déplacer, redimensionner et colorer les terminaux qui y sont, et ajouter des cadres. Avec sessions:write, il peut renommer et étiqueter un terminal, changer ses champs et lui donner un thème de couleurs. Il n’atteint que les projets que son jeton atteint.

L’agent d’un terminal décrit son propre terminal et aucun autre : un nom, un résumé de ce à quoi il sert, ses liens et ses champs, avec aubergine describe, aubergine link add et aubergine field set. Là où vous avez écrit vous-même un nom, un résumé ou un champ, le vôtre reste, et ce que l’agent a envoyé est gardé à côté comme suggestion. Un agent, ou un programme qui a workflows:write, peut aussi proposer un thème de couleurs avec aubergine theme propose : il n’est dessiné nulle part tant que vous ne l’avez pas lu dans Review, vu dessiné, essayé sur la page et accepté, et l’accepter écrit son fichier sans rien choisir.

Les réglages eux-mêmes sont à vous seul. Aucun jeton, terminal ou agent ne peut les changer : PUT /v1/settings/appearance ne répond qu’au navigateur connecté, et appearance.colors, shortcuts et le reste s’écrivent à la main dans le fichier.

Tous ces outils gardent leurs réglages dans un fichier, et VS Code, Zed et Windows Terminal ont aussi un écran qui l’écrit, comme Aubergine. Dans la plupart, un thème est aussi un fichier : du JSON dans VS Code et Zed, du CSS dans Obsidian, du Lua ou du TOML dans WezTerm, un fichier de configuration dans kitty et Ghostty. VS Code, Zed et WezTerm vous laissent changer des couleurs isolées par-dessus un thème, comme le fait ici appearance.colors.

C’est sur le code qu’ils diffèrent le plus. Toute la configuration de WezTerm est un programme Lua, kitty et iTerm2 lancent votre propre Python, et les plugins de Hyper sont du JavaScript qui enveloppe son interface ; Obsidian et Hyper prennent aussi votre propre CSS. Les extensions de VS Code n’ont pas accès au DOM de son interface, et il ne prend en charge aucune feuille de style à vous ; Zed lance les extensions en WebAssembly, avec des capacités que vous pouvez restreindre. tmux, WezTerm, kitty et iTerm2 construisent titres et lignes d’état avec des modèles ou des fonctions.

Aubergine se tient aujourd’hui du côté des réglages : thèmes, couleurs et touches dans des fichiers qui se décrivent eux-mêmes, et une page qui écrit une partie des réglages. Il n’exécute aucun code à vous dans la page, ne prend aucune feuille de style à vous et n’a pas de modèles. Tout cela est sur la feuille de route, et pas construit.

Ce qui est prévu

Une apparence pour un projet ou une étiquette, des modèles, un custom.css et des extensions sont prévus et pas encore construits : voir la feuille de route.

Questions

Chaque terminal peut-il avoir un thème de couleurs différent ?

Oui. Theme… dans le menu d’un terminal dessine son corps dans l’un des dix thèmes, quel que soit celui de la page. Les autres suivent le thème par défaut que vous réglez pour les terminaux, ou la page.

Puis-je ajouter mon propre CSS à Aubergine ?

Pas aujourd’hui. Des couleurs isolées se règlent à la main dans le fichier de réglages ; un custom.css avec des points d’accroche documentés est prévu, non construit.

Où est le fichier de réglages d’Aubergine ?

C’est config.json dans le dossier de données d’Aubergine. aubergine settings path affiche où, et le serveur l’affiche à son démarrage.

Un agent peut-il changer l’apparence d’Aubergine ?

Pas les réglages : ils sont à vous seul. Un agent peut nommer et décrire son propre terminal et proposer un thème de couleurs, qui attend que vous le lisiez et l’acceptiez ; un programme dont le jeton d’API le permet peut renommer, étiqueter et donner un thème aux terminaux, arranger les canevas et proposer lui aussi un thème.

Opérationnel en cinq minutes

Il vous faut macOS avec tmux 3.2 ou plus récent et Node.js 22 ou plus récent. brew install tmux node installe les deux.

npm install -g @meatgarden/aubergine
