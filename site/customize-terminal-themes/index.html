Customize terminal themes, colors, fonts and keys

Choose the page's colors from ten themes, give each terminal a theme of its own, and set single colors, the terminal's font and cursor and every key, in Settings or in one settings file that describes itself.

Ten color themes, light and dark

Settings → Appearance starts with three choices: Light, Dark and Match the system, which is where a new install starts and which follows the system when it changes. Under them you choose a theme of each kind: Light, High contrast light, Solarized light or Gruvbox light; Dark, High contrast dark, Solarized dark, Gruvbox dark, Nord or Dracula. Each is shown with a small picture of its colors.

A change applies at once to the page and to every terminal, without a reload, and is kept in the settings file, so every browser you open Aubergine in agrees. The palette has the same as commands, such as Color theme: Nord.

A different color theme for each terminal

Theme… in a terminal's menu draws that terminal in any of the ten themes, whatever the page is drawn in. Only its body changes: its title, its note and its details stay as the page is. A terminal without a theme of its own follows Terminal theme in Settings, the default for terminals, and without that, the page.

The same choice is in the terminal's row menu in the list, in its details and in the palette. A terminal and a frame can also have a color of their own, one of thirteen or Your own… for any color, and so can a canvas's tab; a terminal's color is its row's in the list too.

Set single colors by hand

Beyond the themes, 35 colors of the page can be set in the settings file, config.json, under appearance.colors: a color's name and a value written #rrggbb. Written at the top, a color is over every theme; written under a theme's ID in brackets, such as "[nord]", it is over that theme alone, and wins.

{
  "$schema": "./config.schema.json",
  "appearance": {
    "colors": {
      "accent": "#c678dd",
      "[nord]": { "terminal-bg": "#242933" }
    }
  }
}

The names are the page's color tokens, such as bg, text, accent and terminal-bg; docs/design.md lists them. A wrong entry is skipped, and the rest of the file still counts; Settings → Appearance says which was skipped. Colors you set are yours: nothing checks that what you wrote can be read.

Themes of your own, as files

A theme of your own is a JSON file in themes/ in the data folder: one of the ten as its base, of the same kind, with any of the 35 colors over it, and a terminal's own colors: its words, the cursor, what is selected, and the sixteen colors a program asks for. It is listed after the ten of its kind, marked yours, and can be chosen wherever they can: for the page, as the default for terminals, or for one terminal. Shadows and the focus ring stay the base's, and nothing in a file is run.

{
  "$schema": "../theme.schema.json",
  "name": "Harbor",
  "kind": "dark",
  "base": "nord",
  "colors": { "bg": "#0e1a24", "accent": "#5fb3b3" },
  "terminal": { "foreground": "#d8dee9", "cursor": "#5fb3b3" }
}

aubergine theme new harbor --from nord writes a file to start from, with every color of the theme it is from; aubergine theme check says what is wrong in one; Read themes again in Settings picks up a change. Whether your colors can be read is yours to judge: Settings only says when text may be hard to read. docs/themes.md has the format.

Fonts, cursor and keyboard shortcuts

Terminal text in Settings → Appearance sets the size of a terminal's text, from 8 to 32 pixels, and its font, as a list of which the first font found is used. Cursor sets its shape, block, bar or underline, and whether it blinks.

Every key can be changed. Add shortcuts to the settings file: a command's name with a chord, a list of chords, or null for no key. shortcutsInAppWindow takes the same and applies only where Aubergine is installed as an app with a window of its own. Reload the page, and the shortcut sheet (?), the palette and the tooltips show the keys as you set them.

{
  "shortcuts": {
    "terminal.park": "X",
    "attention.next": ["Ctrl+Cmd+G", "W"],
    "view.fit": null
  }
}

A key set twice, or one that cannot be read, is reported at the top of the shortcut sheet and by the server, and the rest of the file still applies. A plain key, or Ctrl or Option with a key, works only while no terminal has the keyboard, so that every program in a terminal still gets the keys it needs. More in Keyboard, in the README.

One settings file that describes itself

All of this is kept in config.json in Aubergine's data folder, and aubergine settings path prints where that is. Every key may be left out. A file that cannot be read means the defaults, never a server that will not start. Settings in the page writes only the keys it changes and leaves the rest of the file as you wrote it.

Each time it starts, the server writes config.schema.json beside the file. Add one line, and an editor that reads JSON Schema describes and completes every key:

{ "$schema": "./config.schema.json" }

aubergine settings list prints every key with its value now, marked where it is not the default, and aubergine settings schema prints the schema. docs/settings.md describes every key, its default, and whether Settings writes it or you do.

aubergine settings path
aubergine settings list
aubergine settings schema

In the page, Settings → Every setting lists the same keys with their values, and finds them as you type. A key that Settings changes takes you to its control; a key written by hand has Copy, for the line to add to the file. Nothing there changes a setting.

Some choices belong to this browser and are kept there: whether the canvases are tabs, one list or a column; where the bar over the canvas stands and whether it stays open; whether the side panel and the map are folded; the widths of the panel and of a terminal's details; and how the list of terminals is filtered, grouped and sorted.

What a program or an agent may change, and what stays yours

Through the local API, a program with an API token may arrange canvases with canvases:write: name, color and order them, move, resize and color terminals on them, and add frames. With sessions:write it may rename and tag a terminal, change its fields and give it a color theme. It reaches only the projects its token reaches.

The agent in a terminal describes its own terminal and no other: a name, a summary of what it is for, its links and its fields, with aubergine describe, aubergine link add and aubergine field set. Where you wrote a name, a summary or a field yourself, yours stays, and what the agent sent is kept beside it as a suggestion. An agent, or a program with workflows:write, may also propose a color theme with aubergine theme propose: it is drawn nowhere until you have read it under Review, seen it drawn and tried it on the page, and accepted it, and accepting writes its file and chooses nothing.

The settings themselves are yours alone. No token, terminal or agent can change them: PUT /v1/settings/appearance answers only the signed-in browser, and appearance.colors, shortcuts and the rest are written by hand in the file.

Every tool here keeps its settings in a file, and VS Code, Zed and Windows Terminal also have a screen that writes it, as Aubergine does. In most of them a theme is a file too: JSON in VS Code and Zed, CSS in Obsidian, Lua or TOML in WezTerm, a configuration file in kitty and Ghostty. VS Code, Zed and WezTerm let you change single colors over a theme, as appearance.colors does here.

They differ most in code. WezTerm's whole configuration is a Lua program, kitty and iTerm2 run your own Python, and Hyper's plugins are JavaScript that wraps its interface; Obsidian and Hyper also take your own CSS. VS Code's extensions have no access to its interface's DOM, and it supports no style sheet of yours; Zed runs extensions as WebAssembly, with capabilities you can restrict. tmux, WezTerm, kitty and iTerm2 build titles and status lines from templates or functions.

Aubergine today is at the settings end: themes, colors and keys in files that describe themselves, and a page that writes part of the settings. It runs none of your code in the page, takes no style sheet of yours and has no templates. Those are on the roadmap, and not built.

What is planned

A look for a project or a tag, templates, a custom.css and plugins are planned and not built: see the roadmap.

Questions

Can each terminal have a different color theme?

Yes. Theme… in a terminal's menu draws its body in any of the ten themes, whatever the page is drawn in. The others follow the default you set for terminals, or the page.

Can I add my own CSS to Aubergine?

Not today. Single colors can be set by hand in the settings file; a custom.css with documented hooks is planned, not built.

Where is Aubergine's settings file?

It is config.json in Aubergine's data folder. aubergine settings path prints where, and the server prints it when it starts.

Can an agent change how Aubergine looks?

Not the settings: they are yours alone. An agent can name and describe its own terminal and propose a color theme, which waits for you to read and accept it; a program whose API token allows it can rename, tag and theme terminals, arrange canvases and propose a theme too.

Up and running in five minutes

You need macOS with tmux 3.2 or newer and Node.js 22 or newer. brew install tmux node gets both.

npm install -g @meatgarden/aubergine
