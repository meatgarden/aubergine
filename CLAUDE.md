# Aubergine — project rules

Aubergine is a local, browser-based set of canvases, shown as tabs, where each terminal session is a node you can arrange and use. It is built in small stages; each stage is usable on its own.

## The four seams

These are the only abstractions in the code base. Each has exactly one implementation. Do not add another interface until a feature needs it.

1. **Wire protocol** — `shared/src/protocol.ts`. Every message between a client and the daemon is a versioned zod schema: HTTP bodies, change events, terminal WebSocket messages, and the URL paths themselves. The web app reaches a server only through `web/src/api.ts`, and the terminal socket in `web/src/TerminalView.tsx` opened by it (`openSocket`). The CLI (`daemon/src/cli.ts`) uses the same HTTP protocol; it does not reach into the daemon's state. Agent-facing routes live under `/v1`, and `SESSION_ENV` names the variables each session receives; `aubergine note` and `aubergine hook` use only those routes. `CreateSessionRequest` also takes `cwd`, `command`, `uniqueName`, `agentContinue` and `agentArgs`. `EventsServerMessage` has a `show` message, which is not a change event. `/v1` also has `PUT …/agent`. The three `/api/v1/outside` routes (list, add, move) and their schemas are part of the protocol too. So are `publicPaths` and the public schemas (`CanvasSummary`, `CanvasDetail`, `pageOf`, `PageQuery`, `IDEMPOTENCY_HEADER`), `PATCH /v1/sessions/<id>` and `tags` on the create requests, `canvasAddress`, the `viewing` message a browser sends on the events socket, `canvasId` on `CreateSessionRequest`, `CreateFrameRequest`, `OutsideTarget` and restore, and `defaultCanvasId` in the state response. Since API tokens: `publicPaths` also has `root`, `sessions`, `session`, `parkSession`, `restoreSession`, `showSession`, `showCanvas`, `sessionNotes`, `events`, `tokens`, `token` and `activity`; `EventsServerMessage` has `show-canvas`; error codes include `too_large` and `rate_limited`; the token, scope, activity and capability schemas are in `shared/src/tokens.ts`. Since devices: `paths` also has `pair`, `devices`, `device` and `pairingCodes`, the device and pairing schemas are in `shared/src/devices.ts`, and the state response has `here` (and, since the settings describe themselves, `settingsFile`; since the owner's stylesheet, `customCss` and `customCssProblem`, left out for a linked page). Since linked pages: `paths` also has `socketTickets`; `PairingCodeRequest` takes `kind: 'page'` with an `origin`; `PairedPage`, `SocketTicket`, `TICKET_PARAM` and `LINKED_PAGE_HEADERS` are part of it too, and so are `LINK_NAME` and `linkedAddress` (the page's `/s/<link>` addresses). Every `/v1` route is declared once, in `ROUTES` in `shared/src/routes.ts`: address, method, schemas, the action `authorize` is asked, a summary. The server registers handlers from that list (`daemon/src/v1.ts`), and the description of the API (`/v1/openapi.json`), the client and the reference are generated from it by `daemon/src/describe/`.
2. **`SessionRuntime`** — `daemon/src/runtime/runtime.ts`. Owns the running shells: `check`, `create` (folder, shell and `env`), `list` (with each session's folder, command and `activityAt`), `has`, `kill`, `attach(viewer)` → byte stream, `snapshot`, `typeLine`, `search`, `reveal`. Resizing is a method of the attachment that `attach` returns, because a size belongs to a viewer. Implementation: `TmuxRuntime`, one tmux session per session ID on a dedicated socket with the config in `daemon/src/runtime/tmux.conf`; each viewer is one `tmux attach` in its own pseudo-terminal. Sessions must outlive the daemon process. Scrollback, copy (OSC 52) and paste handling live in the runtime and in `TerminalView`, nowhere else, so the runtime can be swapped. For programs it also has `screen`, `lines`, `type`, `press` and `foreground`. Reading is `capture-pane` on the session: it attaches no viewer and changes no size. `type` sends the text as bytes (`send-keys -H`); nothing a caller wrote is ever an argument tmux parses.
3. **`Store`** — `daemon/src/store/store.ts`. `load` and `save` of the whole state (`AppState`). Implementation: `JsonStore`, one JSON file written atomically. Each canvas holds its own layout (nodes and frames), which refers to sessions by ID. The file has a version; an older version is migrated on load (`migrate` in `json-store.ts`), a copy of the older file is kept beside it first, and every change of shape needs a fixture of the old file under test. New fields get a zod default so older files still load.
4. **Change events** — `StateHub.emit(event)` in `daemon/src/state-hub.ts` is the only way state changes. It applies the event with `applyEvent` from `shared/`, saves, and notifies subscribers; the browser receives the same events over a WebSocket and applies them with the same reducer. Never mutate state any other way. Events cover sessions (created, renamed, parked, restored, exited, restarted, activity, noted, closed, plus `session.status`, `session.attention`, `session.note.appended` `session.agent`, `session.moved`, `session.times`, `session.tagged` and `session.themed`), canvases (`canvas.created`, `canvas.updated`, `canvas.removed`), nodes and frames; node and frame events carry a `canvasId`.

## Rules

- **Import boundary.** `web/` may import `shared/` but never `daemon/`. `shared/` imports neither, and no Node-only modules. ESLint enforces both (`eslint.config.js`); do not weaken those rules.
- **IDs** are UUIDv7 (`newId()` in `shared/`). Every session has a `projectId`; one default organization → workspace → project exists from the first run.
- **Paths.** The data folder comes from `dataDir()` in `daemon/src/paths.ts` and nowhere else. No hard-coded per-OS paths in other files. The one exception is the start-at-login module below.
- **Settings.** The schema is `Settings` in `shared/src/settings.ts`; the file is `config.json` in the data folder, read by `daemon/src/settings.ts`. A missing or invalid file means defaults, never a failed start.
- **The settings describe themselves.** Every field of `Settings` (and of what it holds) has a `.describe()`; a test walks the JSON Schema and fails on a key without one. The schema of the file is one function, `settingsJsonSchema` in `shared/src/settings-schema.ts`; `docs/settings.md`, `docs/config.schema.json`, the `config.schema.json` the server writes beside the file at start (only when it differs; a failure is a warning), `aubergine settings` and the list in Settings → Every setting are all made from it, and none of them types a description again. The keys the page writes are one list, `PAGE_WRITTEN_SETTINGS`. The list in Settings changes nothing that has no route: a key the page writes is changed by its control above, and one written by hand is copied as a line for the file. Nothing writes `config.json` for the schema; `"$schema"` in it is the owner's.
- **Shell.** Sessions start a login shell: the user's `$SHELL`, or the one named in settings. Do not hard-code a shell. `shellEnvironment` in the tmux runtime builds the base environment; the login shell does the rest.
- **Start at login.** Everything that knows about launchd is in `daemon/src/service/launchd.ts`. A second service manager goes in a file beside it. Tests only inspect the generated file; never install the service from a test or a script.
- **Security.** The daemon binds `127.0.0.1` only. One `onRequest` hook in `daemon/src/server.ts` checks `Host` and `Origin` on every HTTP request and WebSocket upgrade, and requires the owner's sign-in on `/api` and `/ws`: the access-token cookie here, a device's cookie from an outside address, a linked page's credential (a ticket, on `/ws`) from its own origin. New routes must stay behind that hook. The page is sent with one `Content-Security-Policy`, `PAGE_POLICY` in `server.ts`: `frame-ancestors 'none'` (never shown in another page), and `style-src`, `img-src`, `font-src` and `media-src` of this server and inline data only, so that nothing a stylesheet names is fetched from another address. Nothing in it restricts scripts, connections or frames: the page talks to linked servers and opens sockets. `reach.test.ts` holds the exact value.
- **Loopback only, and outside addresses are written by hand.** The bind stays `127.0.0.1`; whatever carries HTTPS runs on the same machine, and Aubergine never terminates TLS. `access.addresses` and `access.pages` are read when the server starts, checked by `accessProblem` in `shared/src/access-addresses.ts`, a wrong entry reported and skipped. No route writes them.
- **Where a request came in is worked out once, from `Host`, in the one hook.** `here` (this computer's own names) or `outside` (the host of an entry in `access.addresses`), else 403. From outside, `Origin`, when sent, must be exactly that entry. No forwarded header (`X-Forwarded-*`, `Forwarded`) is believed for anything. Handlers ask `cameIn`; they do not look at `Host` themselves.
- **The access token is never accepted from outside.** Not as its cookie, not as a bearer, and `/auth?token=` answers 404 there before anything is compared. From outside the owner signs in with a device's cookie only, and a device's cookie signs in nowhere else. API tokens and session tokens on `/v1` are judged the same from both places, and never open `/api` or `/ws`.
- **A device's secret exists once.** `daemon/src/devices.ts`, modelled on tokens: only the hash is stored, compared in constant time against every device, never in a state answer, on the browser's stream (blanked) or on `GET /v1/events` (left out with every `device.` event). A browser device gets it only as an `HttpOnly`, `SameSite=Strict` cookie, `Secure` from outside. A device not used for 90 days stops working. Keep the search of the data folder for a device's secret and a code.
- **Who a device is for is a word, and the server's.** `Device.person` (`PersonName`) is written when the code is made, by the owner's own request, carried by the code in memory and put on the device by the server; nothing the pairing browser sends sets it, no route changes it afterwards, and it is not written into a project file. It gives and takes no right: every device is `{ kind: 'user' }` whoever it is for, and neither `authorize` nor any handler reads it. The activity log says it (`byPerson`) on a line made through a device, a browser from outside as a linked page; nothing done in the page at this computer is written for it. Never describe it as an identity that was checked, or as keeping one person from another.
- **Pairing codes are memory, not state.** `daemon/src/pairing.ts`: never in the state, an event or a log; once, for three minutes, at most three waiting. Every failure of `POST /auth/pair` is the same answer after the same comparisons, a body that cannot be read included. Guesses are counted for the whole server: five wrong withdraw every waiting code, more than ten tries a minute are 429. From `here` a code is never spent.
- **`devices.manage` is the owner's.** In `NEVER_BY_TOKEN`, not a session action, routes under `/api/v1` that take the owner's sign-in only, no MCP tool. A device is the owner (`{ kind: 'user' }`) and may revoke itself. Revoking closes at once every socket and stream that device holds open (`holdOpen` in `server.ts`); a new long-lived answer registers there too.
- **A request from outside never opens anything on this computer's desktop.** The create route answers why with `desktop: true`; the open-on-desktop route is refused. The state answer says `here`.
- **A linked page's request is judged by its `Authorization` header alone.** A request whose `Origin` is exactly an entry of `access.pages` (and not one of this server's own origins) is from a linked page, whatever its `Host`. No cookie on it is looked at and none is set on its answers; a wrong or missing credential is 401, never tried as anything else. It reaches `/v1`, `/api`, `/ws` (by a ticket) and `POST /auth/pair`, and is answered 403 everywhere else. It is never at this computer: `atThisComputer` is false for it, so `here` is false and nothing opens on the desktop.
- **A page device's credential is a bearer from its own origin, and nothing else; a browser device's is a cookie, and nothing else.** Neither works in the other's place, an API token or a session token from a linked page's origin is 401 everywhere, and a page's credential sent from anywhere but the origin it was paired from is 401.
- **CORS names exact origins from the setting.** Only for an origin in `access.pages`: `Access-Control-Allow-Origin` that origin, `Vary: Origin`, on every answer to it, refusals and errors included. Never `*`, never `Access-Control-Allow-Credentials`, and nothing at all for any other origin or for the page this server served. A preflight is answered in the hook before any route, carries no credential, and is not counted or logged.
- **A socket ticket is memory, once, 30 seconds, for one device and origin, and only opens `/ws`.** `daemon/src/socket-tickets.ts`: a hash in memory, never in the state, an event or a log; spent on the first offer that matches; good only while its device is still active and from the origin it was made from. Only a linked page's device gets one (`POST /api/v1/socket-tickets`); nothing but a linked page's upgrade under `/ws/` takes one, and that upgrade takes nothing else.
- **A page's code is spent only from its own origin.** It is made only for an origin in `access.pages`, needs no outside address, and is answered with the credential in the body (`PairedPage`), `no-store`, no cookie. From anywhere else it is the one refusal, and stays.
- **This server never calls a linked page's server.** It answers what a linked page asks; it holds no credential for another server and starts no request to one.
- **The page shows one server at a time, and `showServer` is the one way that changes.** `server` in the store is null for the page's own server or the short name of a linked one; everything the store holds that names something (the whole state, the canvas, focus, selection, the drawer, panels, pages, asks, `following`) is of that server. `showServer` stops the events stream, makes the other the target in `api.ts`, sets all of that back (`NOTHING_OF_A_SERVER`), tells the modules that keep something read from a server (`forgetOnSwitch`), and loads and follows the other. Nothing is merged across servers; what waits is counted for the server shown only. What this browser keeps by canvas, project or session ID (pan and zoom, the last canvas, notes seen) is kept: IDs are unique across servers.
- **Two targets in `api.ts`.** `api` goes to the server shown; `ownApi` goes to the page's own server whatever is shown, and holds only what is the page's own: its settings (`getState`, read for them), `setTheme` and `setLook`, `readThemes` (the owner's theme files, which are about the page as the theme is: `themes` in the store is always the own server's), `readStylesheet` (the owner's stylesheet, the same: `customCss` in the store is the own server's), and its projects for the menu. The settings that are about the page (`PAGE_SETTINGS` in `servers.ts`: the theme, `appearance`, the font, the keys) are the own server's whatever is shown (`withPageSettings`); everything else is the server shown's. `pair` (this browser's own sign-in) goes to the own server.
- **A linked server's credential is sent only to its own origin.** `requestFor` is the one place a request is made: for a linked server, an absolute address at its `address`, `Authorization: Bearer`, `credentials: 'omit'`, `redirect: 'error'`, and it throws, sending nothing, for a path that would leave that origin. The credential is in this browser's storage (`servers.ts`) and in `api.ts`'s memory, and in no address, log, toast, error, title, or request to any other server.
- **An answer or a socket message for a server no longer shown is dropped.** Every call notes the target's generation when it starts; one that comes back under another rejects with `Superseded`, which lands in no store and is said nowhere (`isSuperseded`, wherever a failure is said). A socket opened for a previous target is not listened to and is closed (`socketIsCurrent`).
- **A socket to a linked server is opened with a fresh ticket each time.** `openSocket` asks `POST /api/v1/socket-tickets` before every connection and reconnection, and puts the ticket beside the path's own query. A ticket refused (401) stops reconnecting; any 401 from the linked server shown is said once (`whenRefused`) and the own server is shown.
- **The own server is never told about a linked one.** No request to it holds a linked server's address, label, credential or device ID; the `/s/<link>` address holds only this browser's short name. The browser test "two servers in one page" reads every request and compares the first server's state file before linking and after unlinking.
- **Linked servers are this browser's.** `servers.ts`: one `localStorage` key, read tolerantly (a wrong entry is dropped), each `{ id, label, address, credential, deviceId, addedAt }`, the address an origin by the same rule as `access.pages`, the ID eight lowercase letters and digits from `crypto.getRandomValues`. Where storage cannot be used, linking says so and is not offered.
- **A linked server's address is `/s/<link>/…`**, the own addresses after it (`linkedAddress`; `linkFromPath` and `ofItsServer` read it). While a linked server is shown every address written (`writeAddress`, `canvasHref`, `terminalHref`, `terminalOnCanvasHref`) carries it; the server serves the page for those addresses and learns nothing from them. A `<link>` this browser does not know shows the own server and says so in one sentence. The terminal's own page sets its target from the address before anything is asked.
- **Another version is refused with a sentence.** A linked server whose answers do not parse (`NotUnderstood`), or whose `PairedPage` names another `protocolVersion`, is not shown: the page says that both must be the same, and a device it just made there is revoked. A server that cannot be reached when it is first shown, or no longer takes the credential, sends the page back to its own server with a sentence too.
- **Linking and unlinking are the browser's.** Link a server… sends the code to that server's `/auth/pair` itself (`pairWith`: no credential, no cookie, no redirect) and keeps what it is answered; Unlink forgets the server here first and then asks it to revoke the device, best effort, and says if it could not. Both are commands (`server.link`, `server.unlink`).
- **A directory is a phone book, and the browser's.** A directory lists servers by organization in a JSON file somewhere else. `readDirectory` in `shared/src/directory.ts` is the whole rule of what a file is (bounded, plain names, every address an origin by the rule of `access.pages`, refused whole with a sentence, unknown fields left out) and `directoryAddressProblem` of where one may be. It holds no code and no credential and reading one links nothing: pressing a server only writes its address and name into the fields of Link a server…. What a directory calls itself, a server or an organization is a claim: its host is shown beside it.
- **A directory is told nothing and kept nowhere.** `directoryTextAt` in `api.ts` is the one place one is asked for: no cookie, no credential, no referrer, no redirect, a bound and a time limit. Only its address is kept, in one `localStorage` key of this browser (`web/src/linking/directories.ts`, read tolerantly, five at most); what it says is read when Link a server… opens or one is added, and dropped when the dialog closes. Never on a timer, never when the page loads. No server, own or linked, is told of a directory, and no server reads one.
- **A code in the address is read after `#` and removed before anything else.** `takeCodeFromAddress` in `web/src/devices/pair-address.ts` runs first in `main.tsx`, before any request, and takes a `#pair=` fragment out with `history.replaceState`, a good code or not; `codeFromFragment` is the whole rule of what is a code there. The code is then tried once from the sign-in surface.
- **The page never keeps a code.** Not in `localStorage`, not in a log, not in an address again, not in the store: the sign-in field and the Add a device dialog hold it in their own state, and the dialog drops it when it closes or the code runs out. It is sent in a body only (`api.pair`).
- **A QR code is drawn from its matrix, never from markup.** `qrMatrix` asks the library (`qrcode`, pinned as in the daemon) for the modules only; `qrPath` makes one path of them and `QrCode` draws it as React elements, dark (`--qr-dark`) on light (`--qr-light`) in both themes, with an accessible name and the address beside it as text.
- **What acts on this computer's desktop is left out when `here` is false.** One selector says so, `atThisComputer` in the store: "Open on desktop" (a node's menu, a row's menu, the details), the box in the dialogs that make a terminal, the Settings switch for new terminals, and the terminals open outside the canvas. The two commands (`terminal.openOnDesktop`, `outside.open`) stay registered with `atThisComputerOnly`: left out of the palette, and said not to be available if run. This is so the page does not offer what the server refuses; it is not a control.
- **Not signed in is one field and one button** (`SignIn.tsx`): a sentence that says where a code is made and that `aubergine open --print` signs in a browser at that computer, the field, "Sign in". After a sign-in the page loads as it does at first (`signedIn` in the store); revoking the device the page is on sends it back there.
- **A stranger from outside is walked through every route.** `everyRouteOf(app)` lists all of them; the walk in `reach.test.ts` allows only the page's own files and `POST /auth/pair` to answer anything but 401, 403 or 404. The walk in `linked-pages.test.ts` does the same from a linked page's origin, where only a preflight answers anything else. A new route needs no test of its own for this, and must pass it.
- **Status never depends on a viewer.** Shell state comes from `ShellIntegration` (status files written by shell hooks), not from terminal output. Never edit the user's dotfiles; another shell is another class in `daemon/src/shell/integration.ts`.
- **Authorization.** Every route asks `authorize(principal, action, resource)` in `daemon/src/auth.ts` before it looks at the body or looks anything up, so a caller without the right learns nothing from the answer. There are three principals: the signed-in user, a session, an API token. A token's scopes are looked at in `authorize` only; no route checks a scope or the kind of caller. A new action is closed to tokens until one line in the scope table opens it.
- **One principal per request.** A request with an `Authorization` header is judged by that credential alone: a cookie beside it is ignored, and a wrong credential is refused, never retried as the cookie's owner. `/api` and `/ws` take the owner's sign-in only: the cookie, or a linked page's credential (on `/ws`, its ticket). Never an API token, never a session token. Where a rule here calls a route under `/api` "cookie-only", it means this: the owner's sign-in, never a token.
- **Never by token.** `NEVER_BY_TOKEN` in `auth.ts` lists what no token may do whatever its scopes: creating, listing and revoking tokens, reading the activity log, changing settings, and anything about terminals or processes outside Aubergine. Do not add a scope for any of these.
- **Session tokens do not grow.** A session token may set its own attention, add to its own note log, report its own agent, name its own terminal and write its own summary, read and write its own links, set and remove its own terminal's fields, make the checks its hooks make, read and report on the run it is on, read what it was asked to write, propose drafts and read its own drafts, list the workflows its repository offers, list the color themes there are, propose a theme and read its own proposals, and ask what the server can do. Wider access is an API token the owner makes on purpose. A session token must never reach a canvas, layout or other-session route, another terminal's links, a run by its ID, a list of runs, a draft by its ID or anyone else's draft, the shelf, a workflow, a repository's files or their text, anyone else's proposed theme, accepting anything, or starting any run.
- **A token's secret exists once.** It is returned by the create route and never stored, logged or sent again; only its hash is kept, and the hash is not sent to the browser. Comparisons are constant-time. A test searches every file in the data folder for a secret after using it; keep it passing.
- **`sessions:write` starts plain shells.** Starting a session with a command also needs `terminal:input` reaching the new session. Every description of these scopes (README, `SCOPE_MEANING`, the token screen) must say plainly what can run commands.
- **The activity log is not state.** One JSON line per call made with an API token, through the `ActivityLog` interface in `daemon/src/activity.ts`, in its own file with a size cap. It records who, what and how it ended; never the secret, never a request body or query. Nothing else reads or writes that file.
- **Limits** (`api` in settings) are read when the server starts. Refusals use the one error shape: 429 with `Retry-After`, 413.
- **Public routes are walked by tests.** `publicRoutesOf(app)` lists every `/v1` route; the tests try each with a read token, a token without `read`, a token with every scope, and a cross-origin browser. A new route needs no test of its own for these, and must pass them.
- **`GET /v1/events` is the stream for programs** (server-sent events) and leaves token events out; the WebSocket under `/ws` stays the browser's.
- **A run moves in one place.** `stepRun` in `shared/src/workflows.ts` is the only code that knows how a run goes from one state to the next, and `Workflows.apply` in the daemon is the only caller that saves the result. A button, a command and a route all send a report. Do not change a run any other way.
- **Workflow versions are never changed.** Editing a workflow appends a version. A run points at one; do not make a run follow the latest.
- **What an agent is told is one function.** `renderRun`. The preview, the route answers and `aubergine workflow status` all use it; do not build that text anywhere else.
- **Element kinds and run views are registered.** Nothing compares a kind to a name. A new kind is `registerElementKind` in `shared/` and `registerElementView` in the web app; another way of looking at a run is `registerRunView`.
- **Finished runs are not state.** They go to the archive through the `RunArchive` interface, into the archive first and out of the state second, and are read a page at a time. The browser holds live runs only.
- **A report is one event about one run.** Nothing rescans runs on a report. The terminal list is worked out again for a run only while a filter that looks at runs is on (`usesRuns`); a strip listens to its own run.
- **Only fixed sentences are typed.** `KICKOFF_LINE`, `BRIEF_LINE`, `RECAP_LINE` and `INBOX_LINE` in `shared/` are the only things `Sessions.tell` types for workflows, drafts, recaps and messages, and the only text added to an agent's launch line. Nothing stored is in them: not a name, not a description, not a comment. What an agent needs to know it reads with a command. They are typed only for the owner (or, for the kickoff, a token that may type into that session) and only into a terminal an agent runs in. A test collects every line typed and compares it with these. Reporting on a run never types into a terminal.
- **`aubergine` in sessions.** The launcher is written to `bin/` in the data folder with `stableNodePath()` and goes at the end of a session's `PATH`, never the front; the zsh integration puts it back only when no `aubergine` is found. No startup file is edited.
- **Workflow files keep what they do not know.** Unknown fields go into `extra` on import and are written out on export; a change to the format needs the round-trip test to pass.
- **Names are plain text.** A workflow's or element's name passes `PlainName`: one line, no control characters, no characters that reverse text direction. Names are printed in terminals and beside buttons.
- **Tightening a stored schema needs a migration.** A state file that no longer passes its schema is set aside and a fresh state is started. So a rule that makes a schema stricter for anything already stored must come with a new state version and a migration that repairs old values, and a test with a fixture of the old file.
- **What is not written by the owner is a draft first.** An agent's or a program's workflow or element enters through `Drafts` and can only leave it through `accept`, which is the owner's alone (`drafts.review` is in `NEVER_BY_TOKEN`). No route starts a run of a draft, lists it among workflows, or renders it as a run's text. Do not add a way round the review screen.
- **The review screen knows no source.** It draws what `registerReviewSource` gives it. A new source of things to review is a module that registers; do not add content to `ReviewScreen.tsx`. Accepting waits until the whole text has been shown (`needsShowAll`).
- **What a reviewer reads is what an agent would be told.** `reviewText` goes through `previewRun`. Do not build that text another way.
- **Output kinds are registered**, in `shared/` (`registerOutputKind`) and in the web app (`registerOutputView`). The note stores nothing beyond the element's `note`.
- **A tick is not a report.** `tickRun` changes ticks and nothing else, and also works on a run that is over, through `RunArchive.amend`; the archive file still only grows, and the later line for a run wins.
- **A workflow made to run one element is unlisted** (`listed: false`), left out of every list, and removed when its run ends.
- **Optional fields of a change carry no defaults.** A body that changes part of something must leave what is not sent as it was; a schema with a default turns "left out" into "empty". Build such bodies from fields without defaults.
- **Commands show control characters.** Text that came from an agent, a token or a file is printed through `showControl`.
- **A token's review switch is decided in `authorize`.** `workflows.write` is refused for a token whose changes need review; nothing else looks at the switch.
- **Repository files are read in one place.** `daemon/src/repository-files.ts` decides what may be read: regular files directly in `.aubergine/workflows/`, a bounded number and size, no link followed, opened with `O_NOFOLLOW`. Do not read a repository's files anywhere else, and do not run Git.
- **A folder is read only as the repository of a session.** A `root` sent by a caller must be the repository of some session's folder now; otherwise 404 before anything is opened.
- **Only accepted content runs.** A repository workflow is run from the content stored with its acceptance, after the file was read again and its hash matched. Never from the file. A changed file is reviewed again. Nothing about a repository's files is cached.
- **The server writes into a repository only when the owner asks**, one file, named by `repositoryFileName`, never replacing one unasked, never through a link. `repository.write` and `repository.review` are in `NEVER_BY_TOKEN` and are not session actions.
- **Owner calls from outside the browser are visible.** `ownerCaller` in `server.ts` tells a page (which sends `Sec-Fetch-Site`) from anything else; the actions in `WATCHED` are recorded in the activity log as `owner-cli`. This is a trace, not a control: do not describe it as protection, and do not let anything depend on it for a decision. Tests that call as the page send `Sec-Fetch-Site`.
- **The record of drafts is not state**, like the activity log: `DraftLog`, its own file, never what a draft said.
- **Sessions know their server**: `AUBERGINE_PORT` and `AUBERGINE_DATA_DIR` are in every session's environment beside the others.
- **Terminal access is two scopes, a reach and a switch, all decided in `authorize`.** `terminal:read` and `terminal:input` are implied by nothing. `authorize` is handed the session's canvas, tags and people-only switch in the resource; do not look them up after it. A session token never has either. A token that holds the scope but whose reach does not cover a session is told `out_of_reach`, and told exactly the same about a session that does not exist.
- **People only is the owner's.** `sessions.protect` is in `NEVER_BY_TOKEN` and is not a session action. No route, field or default may let a token or a session change it.
- **Text is typed as it is, or refused.** `inputProblem` in `shared/src/terminal.ts` is the whole rule. Do not add escapes, key names inside text, or cleaning up: what is not plainly text is refused and nothing of the call is typed. Keys come from `NAMED_KEYS` only.
- **Nothing a caller wrote is on a tmux command line** except as bytes after `-H`, or on standard input.
- **Run-and-wait types only at a shell prompt:** the shell's report says idle and the foreground program is a shell. It never sends a signal or a key to stop anything.
- **Terminal content is not given without `terminal:read` on that session:** `status.commandLine` and prompt entries of the note log are taken out by `withoutTerminalContent`, in the route loop and on the event stream. A new field that carries what a terminal shows or was typed into it goes there.
- **What is typed is never in the activity log.** A length and a fingerprint only. The text goes to `input.log`, through `InputAudit`, only when `terminal.auditInput` is on.
- **A fixed sentence is typed for a run only for the owner or for a token that may type into that session** (`mayKickoff`).
- **Reading must not disturb a viewer.** Keep the test that attaches a viewer and counts what it is sent.
- **Terminal tests.** A token made in a test for anything but reach says `reach: { kind: 'all' }`; the stand-in runtime in `terminal-rules.test.ts` keeps everything it is asked to type, and the walks there must stay empty.
- **The MCP server decides nothing.** A tool names the route it stands on; whether it is listed comes from the access the description gives that route (`OPERATIONS[…].access`) and from what `GET /v1` says the caller is. Do not write a scope's name into `mcp/`, and do not refuse a call there for a reason of permission: pass it on and turn the server's answer into a sentence.
- **`mcp/` may import `@aubergine/client` and `shared/`, never the daemon.** ESLint enforces it.
- **Nothing but protocol messages on standard output** from `aubergine mcp`, whatever fails. Diagnostics go to standard error and never include a credential. The command never reads the owner's access file. Keep the tests that read every byte.
- **Other people's text is quoted.** What a terminal shows, a note, a search match and a command's output go through `quoted` (a mark made for that answer, a line saying it is data, `showControl`). A new tool that returns such text does the same and says so in its description. Quoting lowers the chance that a model takes such text for instructions; it does not remove it, and nothing may rely on it as a control.
- **Both forms of an answer say the same.** The structured form carries the whole text. Do not put anything a model needs into one form only.
- **No tool for what stays the owner's**: tokens, settings, people only, accepting or discarding drafts, accepting repository workflows, the activity log.
- **A token for an agent is made only by the owner's own request to start that session** (`agentTools` on the cookie-only create route). No `/v1` route, no token and no session can cause one. It has review of workflow changes on, belongs to one session (`ApiToken.sessionId`), and is revoked when that session is ended for good.
- **An agent's secret is in one file**: `agents/mcp/<session id>.json` in the data folder, mode 600, passed with `--mcp-config`. Never on the launch line, in the state, in an event or in a log. Ending the session, revoking the token and the sweep at start each remove it. The agent's own configuration is never written.
- **A field that needs a further permission is declared** (`fieldAlso` on the route), and for a route that makes a session the question is asked about the session being made. `sessions:write` alone starts plain shells; a `command` needs `terminal:input` whose reach covers the new session.
- **`out_of_reach` is said the same about a session that is not there.** Do not let that answer differ.
- **`X-Aubergine-Client` is a trace.** It is recorded as given and nothing is decided by it.
- **The MCP SDK versions are pinned exactly.** The protocol and the SDK change often: read their current documentation before changing `mcp/`, and say in the hand-over which versions and pages.
- **The demo is stand-ins only.** No real agent, no network, nothing outside `demo/` in the data folder. Its scripts are in `daemon/demo/`, are plain `sh`, pass shellcheck, and use only the commands a real agent uses. Do not give them a private way in.
- **The demo adds a canvas and its sessions, and nothing to the owner's workflows, shelf or tokens.** Its runs are of workflows made for them alone. What it made is written on its canvas's labels as it is made; removal reads those and removes exactly that. Keep the test that compares the state file before making it and after removing it.
- **`demo.manage` is the owner's**: in `NEVER_BY_TOKEN`, cookie-only routes, not a session action.
- **The demo types nothing of its own.** A stand-in is started by the `command` of its new session, like any other. Do not add a path that types into a terminal for the demo.
- **Tour steps are registered.** A step is `registerTourStep`: what it points at, what counts as done, at most two short sentences, a one-line reminder. Do not add content to `Tour.tsx`, and do not name a key combination in a step. The help panel reads the same registry.
- **A tour step waits for the real action.** Where the state does not show that something was done, the place it happens calls `tourSignal`; do not complete a step on a timer or on a click of the card.
- **The tour never blocks.** Its ring takes no clicks, its card is not a dialog and keeps off the buttons of whatever is open (`placement.ts`). It uses timers, not animation frames.
- **Nothing about the tour leaves the browser.** Whether it was finished or put away is one `localStorage` entry. No request, no log.
- **An empty canvas offers three ways to begin**, and its panel must not take clicks meant for the toolbar.
- **An agent's configuration is read in one module per agent kind** (`claude-inventory.ts`), behind `AgentInventory`. It never writes one of those files, never starts the agent's command line or any command a file names, and contacts no server. Do not add a second reader.
- **Names only.** Whatever is shown of an agent's configuration goes through `names-only.ts`: a program's name, an address's host, the names of variables and headers. Never a value, an argument, the rest of a command line or the text of a rule. A new field that is shown gets a function there and hostile samples in its test. The copy as text is built from what is shown, never from the files.
- **Nothing read from an agent's configuration is stored or logged.** Not in the state, not in the activity log, not in a cache. Keep the test that searches the data folder.
- **Configured is not on.** The panel says how an agent is set up, not what the running agent has. Nothing read from files is called "on" unless a file says so by itself (a hook, a plugin, a skill). An MCP server is "configured", "off" or "waiting". Whether one answers is not known and must not be implied, in a label or anywhere else.
- **Not readable and not recognised are said, never shown as empty.** Every file has those two paths, and both reach the top of the panel. A need is "cannot tell", not "not found", when any file could not be read.
- **The gaps are always shown**: connectors from the account, whether a server answers, what the running agent loaded, settings delivered without a file.
- **`inventory.read` is the owner's**: in `NEVER_BY_TOKEN`, not a session action, a cookie-only route, no MCP tool.
- **A need mark is advice.** It compares names, says so, and never disables a button.
- **Withdrawing is the demo's alone.** `RunArchive.withdraw` and `DraftLog.withdraw` are called only by the demo's removal, with the sessions its labels name. The files still only grow; readers leave withdrawn entries out.
- **A hint that is said once** is remembered in the browser, and is not shown at all where it cannot be remembered.
- **The agent's configuration and its documentation change often:** read the current pages before changing `claude-inventory.ts`, and say in the hand-over which version and pages.
- **A recap has two parts, kept apart.** What Aubergine knows is `recapOf`, a pure function of a session and its runs: no agent, no model, no file. What the agent wrote is the session's `recap`, shown as the agent's words with its time, and "may be out of date" once the terminal has printed since. Do not merge the two or build the first anywhere else.
- **A session may write its own recap; no API token may.** `recap.own.write` is a session action and nothing else. `recap.ask` is the owner's.
- **Aubergine calls no model.** A recap is what is known or what the session's own agent wrote. Do not add a summary made by starting an agent or a model call.
- **"While you were away" is memory, not state and not a log.** A bounded window of moments made from change events; after a restart it says it only knows since then. Never the command that failed, only that one did.
- **Conversation records are read in one module per agent kind** (`claude-history.ts`), behind `AgentHistory`. It is given a folder, never a path; it never writes, renames or deletes; it starts nothing.
- **The form of a conversation's lines is not ours.** The product calls it internal and changing. Every line is read as "something that may be a message" by `readLine`; a record none of whose lines is one is "not recognised", never empty. A new field read from a line gets a case in that function's test.
- **Conversations are the owner's alone.** `history.read` and `history.open` are in `NEVER_BY_TOKEN` and are not session actions: cookie-only routes, nothing under `/v1`, no MCP tool. A session cannot read conversations through Aubergine, not even its own.
- **Nothing read from a conversation is stored, logged or cached.** A list, a transcript and a search are read when asked for and dropped when the panel closes. Keep the test that searches the data folder and compares the records byte for byte.
- **A conversation is opened through the launch line**, by an ID that passed `ConversationId` and is kept for that folder, never twice on the canvas without the owner saying so.
- **A search of conversations is bounded and says when it was cut short.** No index, no copy.
- **What a conversation says is shown as text**: through `showControl`, in text nodes, no markup drawn, no address made a link.
- **The guide for agents is one module.** `shared/src/guide.ts`. The command (`daemon/src/cli/guide.ts`), `docs/for-agents.md`, the MCP server's instructions and its guide tool all render it; do not write about what an agent can do anywhere else. A part names the actions it needs from the access table; no scope is written into its text.
- **The guide names only what exists.** A command or a tool it mentions must pass the tests in `daemon/src/cli/guide.test.ts`; a new owner-only action needs words in `OWNERS_ALONE`.
- **The guide is fixed text.** Nothing stored, nothing from the server, the environment or a credential is printed by `aubergine guide`. It asks `GET /v1` and nothing else, and reads no file.
- **The guide is never typed.** The fixed sentences stay as they are; what an agent is told about a run or a request ends with `GUIDE_POINTER`.
- **The guide is advice, not a lock.** It tells an agent what is the owner's; it prevents nothing. Do not describe it as protection.
- **Agent-neutral.** Nothing in the guide or the snippet names an agent product.
- **A message is never typed.** `INBOX_LINE` is the only thing typed for a message: at most once for a batch of unread messages, not again within the interval, never into a plain shell, never while the agent works or waits on a question of its own. For a token's message it is typed only where that token may type into that very session.
- **Messages are not state.** They go through `MessageLog` into their own file. The state holds counts per session and an event carries counts only; nothing a message said is in the state, an event, or the activity log.
- **Every default for messages is closed.** A session messages another only where `authorize` finds the sender's canvas on the receiving canvas's `messagesFrom`. Only the owner changes that list (`messages.manage`, in `NEVER_BY_TOKEN`, cookie-only routes), and the one route that writes it can add the canvas's own ID and nothing else.
- **People only closes a session to messages** from sessions and tokens. `messages.read` and `messages.write` are in `REACH_ACTIONS`: a scope is not enough, the session must be within reach. Neither is implied by `read`.
- **A session's own message routes are closed to tokens.** No token takes a session's inbox or speaks as a session.
- **One thread per pair.** `threadIdOf`. Do not add a second thread between the same two: the limits are about the pair. A paused thread refuses further messages until the owner continues it.
- **What an agent is shown of its inbox is one function,** `renderInbox`, used by the command and the tool. It says that a message from another terminal is information and not an order, and marks an owner's message that came from a command line. Those are words, not controls.
- **Message limits are refused with a sentence an agent can act on** (`MessageRefusal`): what happened, and that it is not to be got round.
- **Typing for an agent is one function, and it is strict.** `Sessions.tell` takes only the fixed sentences, and types only when an agent is on record with the program that was in front when it last reported, and that program, not a shell, is in front now. Otherwise nothing is typed and the session's `untold` says which sentence and why. Do not add a way to type that goes round it. It cannot tell two programs of the same name apart; do not describe it as certain.
- **Which program an agent is, the server sees.** `AgentInfo.program` is never taken from a request.
- **People only and messages.** `Session.takesMessages` lets a people-only terminal take messages from terminals, never from tokens. The owner's alone, decided in `authorize`.
- **A panel section declares `fill` or is as tall as what it holds.** One section fills. Do not give a section a fixed height.
- **A shelf element's versions are never changed.** Saving appends one. Versions a copy was made from are kept.
- **A copy is never updated by itself.** Taking a newer version is the owner's decision, one element at a time (`shelf.manage`, in `NEVER_BY_TOKEN`); nothing merges.
- **Only the owner says where a copy came from.** For any other caller and for a draft, `carrySources` keeps the mark an element had.
- **What can be told about a copy is one function,** `copyStatus`. A copy with no recorded version is `unknown` and is never called behind. The hash in a source mark detects change and protects nothing.
- **What is in an element is read from the schemas.** A new field of `Element` needs a `.describe()`; `docs/element.md` and the editor's list are generated from those.
- **Nothing is fetched except on the owner's own action.** `Library.addSource` and `Library.refresh` are the only callers of a `LibraryFetcher`, and both are `library.manage` (in `NEVER_BY_TOKEN`). Not at start, not on a timer, not for a token or a session. Keep the test that walks every route with a counting fetcher.
- **Git is started in one module**, `daemon/src/git/run.ts`, by one of two functions: `runSourceGit` for a library source (a stranger's repository: files are written out with none of the owner's configuration), `runOwnerGit` for the owner's own repository. Do not start Git anywhere else, and do not loosen one function's rules for the other's use. `daemon/src/library/git.ts` remains the only caller for fetching, behind `LibraryFetcher`: getting commits uses the owner's configuration and is the only step with a network; writing files out uses none and has no network. Do not merge the two steps. Read the installed Git's manual before changing an option, and say in the hand-over which.
- **Nothing fetched is run, and it is read in one place.** A source's index and files are read with `readInside` in `repository-files.ts`. Do not read a source's files anywhere else.
- **An address is only an address.** `gitAddressProblem`, checked where it is taken in and again where it is used; always after `--`. No credential is stored, logged or asked for; an address with a password is refused.
- **Nothing installs without the owner accepting that exact content.** `Library.accept` takes the digest that was shown and reads the file again. No route installs any other way, and no token accepts.
- **A refresh never changes what is installed.** It changes what is known about sources, and the state of an installed item at its source; never its content, its workflow or its shelf element.
- **Update is told from the publisher's version and the digest** (`standingOf`). Versions are compared for being the same, never for order. The shelf's counter plays no part.
- **Kinds are registered, of sources and of items.** `registerSourceKind`, `registerLibraryKind` (in `shared/`), `registerLibraryInstaller`. No screen and no route compares a kind to a name.
- **The index keeps what it does not know.** `aubergine library export` writes unknown fields back, writes only inside the folder the owner named (`writeInside`, never through a link), and never commits or pushes.
- **The review is the control, and the only one.** An item of the library is instructions an agent will follow with everything that agent may do. The options given to Git keep a source from running anything while it is fetched; they say nothing about what an item asks for. Do not describe the library as safe to install from.
- **A kind says whether it waits for a person.** `waitsForPerson` on its registration. The step function, `renderRun`, the board and the editor ask that; nothing compares a kind to a name. A new kind that waits is a registration in `shared/` and a view in the web app.
- **Only a person decides.** `runs.approve` is in `NEVER_BY_TOKEN` and is not a session action. `approve` and `send-back` are not in `RunReport`; `stepRun` refuses them, and a jump off or over an element that waits, for any actor that is not a person. Do not add a report, a field or a default that finishes such an element.
- **A decision types only the kickoff sentence**, through `Sessions.tell`, and only when the run is running afterwards. A person's comment is read with the command and is never typed.
- **A person's words are marked as theirs** in `renderRun`, and a comment passes `RunComment`: one line, no control characters.
- **An approval is not a lock.** An agent that runs as the owner can decide as the owner; that is recorded, not prevented. Do not describe approvals as protection against the owner's own agent.
- **The board is one function.** `boardOf` in `shared/src/board.ts`. The screen, the route, the command and the tool show what it returns; do not lay runs out anywhere else. The Runs page's columns are `runLanesOf`, beside it, made from what `boardOf` returned: a run a task stands for is shown as its task, and a run that waits for a person or is blocked is on the owner's list. It holds nothing that the lists of runs, sessions and canvases do not give the same caller.
- **The board does not poll.** It is drawn from the page's state; ended runs are read when it opens and when the number of live runs changes.
- **Starting on several is the existing start, several times.** No session is typed into except by the rule for one run.
- **A source's own name is a claim.** `LibrarySource.claims` is what its index says and never becomes `name`; lists use `sourceLabel`.
- **Where a session works is a registered kind.** `registerEnvironmentKind` in `daemon/src/environments/`. The session code, the routes and the screens ask the registry and the record; none compares a kind to a name. A kind gives its own title, its own words for how far it keeps an agent apart, and its own endings.
- **Kept apart, never more.** A working copy is not a boundary: the agent runs as the owner. No screen, command, document or kind's words may say locked in, sandboxed, isolated or safe.
- **No hook runs for a command Aubergine starts in the owner's repository**, nothing prompts, nothing reaches a network, and reading writes nothing. The owner's filters do run; say so wherever it matters.
- **The owner's checkout is never touched.** Aubergine does not stash, commit, merge, rebase, push, switch or reset there. Keep the test that compares it byte for byte.
- **Names for Git are made, never taken.** `copyNames`; checked again in `git/copies.ts`.
- **A working copy is never removed because its session ended.** Removing or discarding is `environments.manage`, in `NEVER_BY_TOKEN`, not a session action; the second question is asked by the server, and `--yes` does not answer it.
- **A difference is content**: `terminal.read` within reach, and only for a file the environment lists as different.
- **What changed is not read on a timer.** On request, and on a change of the session's status or attention, at most once in ten seconds. Counts are state; file names are not.
- **What a session is told about where it works is one function**, `whereWords`. Session tokens may read where their own session works (`environment.own.read`), and nothing else about environments.
- **A task moves in one place.** `stepTask` in `shared/src/tasks.ts` is the only code that knows how a task goes from one state to the next, and `Queue.apply` in the daemon is the only caller that saves. A task follows its run through the change events; do not change a task any other way.
- **Dispatch is one function.** `nextToStart`. A terminal is given a task only where `isFreeAgent` says an agent is seen in front and is free. Nothing starts a task by itself unless `automatic` is on, or the task is `unattended` (the owner arranged it beforehand: a time of a schedule, Run now), and then only on a change event that could free a place or says an agent may be free: never on a timer.
- **Nothing retries.** A failed task is put back by the owner or not at all.
- **Starting a task is the existing start of a run.** No new sentence is typed for the queue.
- **What an agent or a program adds waits for the owner.** A task from a session or a token is `proposed`, unless the token has review off. Accepting, declining, reordering, starting, the limit, the hold and automatic starting are `queue.manage`, in `NEVER_BY_TOKEN`, and not session actions.
- **Rules are the owner's.** `rules.manage` is in `NEVER_BY_TOKEN`. Action kinds are registered (`registerActionKind`, and `registerActionView` in the page). No action calls an address or runs a command; `run-element` starts a run by the existing start and Aubergine holds no credential for any app. The server calling out to a network is a stage of its own, with its own review.
- **A rule cannot set itself off.** What is added by a session on a run a rule started is marked `viaRule` by the server, never by a caller, and fires nothing. A rule fires once per happening, at most `RULE_RATE_PER_MINUTE` times a minute, and every firing is in the activity log without what the task said.
- **The owner's list is one function.** `forYou` in `shared/src/for-you.ts`, over registered kinds (`registerForYouKind`). A gathered item is never ticked. The toolbar's count and "next waiting" are `sessionsWaiting`, the same function the list's terminal items come from; do not count waiting terminals anywhere else.
- **A session reads only its own of the two lists**: every task by title and state, what it proposed and what it asked. Its three routes are closed to tokens. The owner's list holds other terminals' questions, so it is not a session's to read.
- **Sources are registered** (`registerTaskSource`); nothing compares a source to a name.
- **Ended tasks are not state.** They go to `TaskArchive`, into the archive first and out of the state second.
- **One timer starts something, and it is in one module.** `daemon/src/schedules.ts` holds the only timer in the server that leads to a start. It is set only while a schedule is switched on, wakes once in `WAKE_EVERY_MS`, asks `dueSchedules`, and adds a task or says why not. It does nothing else, and it starts no run itself. Every other "never on a timer" rule stays as it is. Do not add a second timer, and do not make this one do more.
- **Deciding when is one function.** `dueSchedules` in `shared/src/schedules.ts`, given the time and the zone. Nothing else compares a schedule to a clock. A schedule is a time of day and days of the week: no expressions, nothing more often than once a day.
- **No test waits on the real clock for a schedule.** The clock and the timer are a `ScheduleClock` that the test moves.
- **A schedule answers for one time at most.** Whatever passed while nobody looked, it fires once, late, if that time is within `schedules.lateWithinHours`; otherwise it is missed. While the task of its earlier firing is not over it is skipped.
- **A firing is a task.** It goes through `Queue.add` and the queue's own start. The limit and Hold count for it. Nothing about a schedule starts a run any other way.
- **`unattended` is the server's.** No request body sets it. The run such a task becomes is marked like a run a rule started, so what its agent adds fires no rule.
- **Schedules are the owner's.** `schedules.manage` (make, change, switch, remove, run now) is in `NEVER_BY_TOKEN` and is not a session action. `schedules.read` is `read`. A session cannot read schedules.
- **A schedule that cannot run says so once.** One item on the owner's list for as long as it lasts, not one for each of its times; each time is in the activity log, with the caller `schedule`, and never with what the task says.
- **Aubergine calls nothing for a schedule.** It holds no credential and reaches no network: the agent that takes the task uses its own tools.
- **A source may say where its task's result came from.** `says` on a registered task source; the owner's list asks that, and compares no source to a name.
- **A program is started on the owner's desktop in one module.** `daemon/src/desktop/open.ts`, behind `DesktopOpener`. A kind of application is `registerDesktopKind`. It opens a file; it scripts no other application and types nothing. No test opens a real application: the server is given a stand-in opener, or the opener a stand-in `start`.
- **The script holds nothing a caller chose.** `scriptFor`: one command, the session's ID parsed again as an ID, and this server's own port, folders and socket, each through `shQuote`. No name, title or folder of a session. The file is mode 700 in `desktop/` in the data folder, removed when the session's shell ends, and swept at start.
- **A command of the owner's is started without a shell.** Split once by `splitCommand`, the file put where `{file}` is as part of one argument. Do not add expansion or escapes.
- **Opening on the desktop is the owner's.** `desktop.open` is in `NEVER_BY_TOKEN` and is not a session action. A session made by a token, a task, a schedule or a rule never opens a window: only the cookie-only create route does, and only when the request says `desktop: true`. The server does not decide that from the setting; the page does.
- **The page writes four kinds of setting, each by its own route.** `PUT /v1/settings/desktop` changes `desktop.openNew`; `PUT /v1/settings/describing` changes `describe.remind`; `PUT /v1/settings/appearance` changes how the page looks: `theme`, `appearance.light`, `appearance.dark`, `appearance.terminal` (null: as the page is), `appearance.byTag` (the whole list, which replaces the one there was), `appearance.cursor`, `appearance.cursorBlink`, `appearance.titleFormat`, `appearance.rowFormat` (templates: one line of at most 200 characters, no control characters; another is 400), `appearance.customCss` (whether the owner's stylesheet is linked), `font.family` and `font.size`, each only when it is sent, none naming anything that is run. A fourth, `PUT /v1/settings/plugins`, changes one entry of `plugins.on` (a plugin's digest as the server reads it at that moment, `follow`, or none): it names code that runs in the page as the owner, never anything the server starts, and it is `plugins.manage`, the owner's alone. All leave the rest of the file as it was. `appearance.colors` is written by hand and by no route; so are which application and a command line. Do not add a route that writes a command the server will start, and do not add a key without a rule for it.
- **"Also on desktop" is counted, not guessed.** `outsideViewers` comes from the runtime: the clients of a session less the ones the runtime attached. It says that something outside is attached, never which program. Do not set it from having asked for a window.
- **A window that could not be opened never fails the terminal.** The terminal is made and the answer says why.
- **Sizing is the runtime's.** Two views of a session share one size (`window-size latest`). Change it in the runtime's configuration and nowhere else, and change what the page says about size with it.
- **Everything is of one project or shared.** Canvases, sessions, tasks, written items, rules, schedules, runs and working copies carry `projectId`, set by the server from where the thing is made. Workflows, shelf elements, library sources, installed items and tokens carry `projectId` or null. A new stored thing says which it is.
- **`visibleIn` is the one test of what a project may see** of a shared kind, and `stateOf` the one view of the state for a project. Do not filter by project any other way in a pure function.
- **`home` and `host` are asked about in two functions.** `isLocalHome` and `isLocalHost`. Nothing else reads them, no request sets them, and everything that starts a shell, types, reads a terminal or a folder asks first (`Sessions.here` for a session). A new place that touches a folder or a shell asks too. Not asked yet, and to be done before anything remote exists: what changed in a working copy, an agent's configuration and past conversations, the refresh of sessions, terminals outside the canvas, and archiving, removing and moving.
- **A request is about one project.** The loop in `v1.ts` works it out once: of what the address names, else what the request names (the query, the body, or the header `X-Aubergine-Project`), else the first the caller reaches. Handlers take it from the context (`project.id`, `project.scope`); a service that makes a shared thing asks `projectNow`. Do not work it out again in a handler.
- **A token's projects narrow everything.** Decided in `authorize` (the resource's `projectId`), on what a request names (`namesOutOfReach`), and on every answer and every change on the stream (`withinReach`). A thing out of reach is answered as not there. A new route needs nothing for this, and must pass the walk in `projects.test.ts`.
- **Projects and sharing are the owner's.** `projects.manage` and `sharing.manage` are in `NEVER_BY_TOKEN` and are not session actions. A session reads its own project and no other.
- **The queue, the owner's list, the board, schedules and rules are per project.** The limit, hold and automatic are a project's own. A rule hears its own project; a schedule fires into its own. An archived project starts nothing and says nothing.
- **Kinds of what is shared are registered** (`registerSharedKind`). The sharing page knows none by name.
- **A canvas changes project only by the owner moving it**, and its terminals, their runs, their working copies and the tasks that wait for them go with it in one change event (`canvas.project`). A terminal does not move to a canvas of another project.
- **The page shows a view.** `app` in the store is the project being looked at, worked out from `whole` by `viewOf`; a screen that shows every project says so and reads `whole`. What waits is counted over `whole`.
- **Addresses.** `/p/<project>/c/<canvas>`; the canvas decides, so `/c/<canvas>` and an address with a stale project still lead to the right place.
- **A terminal by itself is `/t/<session>`** (`terminalAddress`), the focus view. It names no canvas, shows the terminal through the same `TerminalView` and socket as a node (with `chords={false}`: no canvas key is kept back), and starts no key listener. It never writes a canvas into its address.
- **The focus view follows changes and is never asked to show anything.** It joins the events socket, so its name, its state, its details and its note are live, and it never sends `viewing`. `Viewers` asks only a tab that has said which canvas it shows (`show`, `show-canvas`); a tab that has not said is told of changes and notifications and nothing else. Do not make the focus view say `viewing`, and do not let `Viewers` fall back to a tab that has not.
- **The focus view has three columns, all closed until asked for** (`web/src/focus-view.ts`, one `localStorage` entry of this browser, nothing remembered means closed): the canvases of the terminal's project at the left, each a link to its canvas with the one the terminal is on marked; the terminal's details beside it, the same `Details` as the drawer (`standalone`: what needs the canvas's screens, a run's dialog, past conversations, how the agent is set up, the Type tab, is left out and "Show on its canvas" is the way to them); its note at the right, the same `NotePanel` as beside a node. The terminal has what room is left. Do not write a second details or a second note for it.
- **The focus view's head has its terminal's color**, drawn as the node's title draws it on the canvas, from the same function a list row's color comes from; the default color is the head as it was.
- **The focus view's head begins with the app's name**, the same piece as in the top bar (`.brand`), before Canvases: a tab that shows one terminal still says what it is a tab of. It is not pressed; "Show on its canvas" is the way back.
- **The note is in the focus view once.** While its Note column is open, the details beside it leave out the summary and the Log tab.
- **What the focus view shows is its terminal's project** (`viewOf` asks the terminal's `projectId` there, since the page looks at no canvas).
- **Opening in a new browser tab is `openInNewTab`** in `web/src/address.ts`, with `noopener`, and only for this app's own addresses. A canvas tab opens in one from its menu, from a click with a modifier and from the middle button; a terminal from its title's menu, its row's menu and the palette (`canvas.openInNewTab`, `terminal.openInNewTab`).
- **The bar of tabs scrolls sideways, so nothing may hang from it.** A menu or a palette opened from it is placed against the window (`position: fixed`, from the button's rectangle), as the project menu and a tab's color palette are. A browser test that only clicks does not notice a menu that is cut off: check that the menu is what is under its own corners.
- **Changes are numbered and told in order.** `StateHub` counts its changes from the start of the server (`revision`, under an `epoch`) and tells its listeners of them in the order they were made. The whole state and every change on the browser's stream carry the number. The state and its number are read in the same turn.
- **The page follows in one function.** `web/src/following.ts`: an older whole state is never taken, a change is applied once and in its place, a change before the first whole state waits for it. The store changes `whole` no other way.
- **Several changes that belong together are one step.** `StateHub.atomically`: all of them or none, saved once, told afterwards. Nothing inside it may wait.
- **A project file never holds** what ran, a credential, a setting, or a path or ID of the computer it was written on. Keep the test that searches the text. A new field of a project, a session, a rule or a schedule is not written into the file unless it is added to the format on purpose.
- **No path from a file is a path.** Folders are named places; where a place is, is what the owner said on this computer, and a subfolder is below it.
- **A file is read in one function** (`readProjectFile`): bounds, plain names, references that name one thing each. A file that is wrong in any way is refused whole, with a sentence.
- **Nothing is made from a file before the owner accepts its digest.** `projects.manage`; no token, no session. A template is the same file and goes the same way: one reader, one review source, one maker.
- **Reading a file in starts nothing.** A terminal is made without a shell unless the owner asked; an agent is never started; schedules and rules arrive off.
- **The review screen draws a source's choices** (`Choices`) and still names no source.
- **A test that waits on the server waits for what it reads.** A line in the activity file, a view that follows an event: poll for it. Several tests failed only on a busy machine because they read at once.
- **Canvases.** A session is on at most one canvas; a parked session is on none and remembers where it was (`parkedFrom`). Closing a canvas never ends a shell: the caller says move or park, and the last canvas cannot be closed. Where no canvas is named, `Sessions.canvas(null)` decides (most recently looked at, else first); do not pick a default anywhere else.
- **Public shapes.** Routes under `/v1` use one error shape, `pageOf` for every list, ignore unknown fields, use ISO times, and take `Idempotency-Key` on creates. Do not add a `/v1` route that departs from these. This API is public: only add to it; never rename or remove.
- **A `/v1` route is a declaration and a handler.** Add the entry to `ROUTES` and a handler of the same name in `v1.ts`. Do not call `app.get`/`app.post` for anything under `/v1`: a route registered by hand is not in the description, and the tests fail on it. A handler does not decide who may call it and does not parse its own input; the loop does both, in the order parameters, `authorize`, query and body, handler.
- **The scope table is in `shared/src/access.ts`.** `authorize` and the description both read it. A new action is a line there; a scope is never written into a route, a handler or the docs.
- **Generated files are committed and never edited.** `client/src/generated.ts` and `docs/api.md` are written by `pnpm generate` from the declarations. After changing a route or a schema, run it and commit the result; `pnpm check` fails otherwise. Nothing is generated at install time.
- **Schemas must be describable.** A schema used by a `/v1` route has to survive `z.toJSONSchema`: use `.overwrite` rather than `.transform` to tidy a value, and `.describe()` for what a field means.
- **Answers match their declarations.** Under the test runner every `/v1` answer is checked against its route's response schema, so a handler that returns something else fails whichever test calls it.
- **The client has no dependencies** and uses only `fetch`. Its hand-written part is `client/src/runtime.ts`; everything about particular routes is generated. The command line and the web app make their `/v1` calls through it.
- **Agent hooks** always exit 0 and print nothing of their own. The one thing a hook may print is what the server answers a check with (`hookOutput`): at the start of a conversation, the fixed lines on describing a terminal; at a stop, once in a turn, the form that asks the agent to go on with the fixed sentence saying what is missing. Nothing stored is in either. A check that fails prints nothing. Agent settings are generated into the data folder and passed on the command line; never write to an agent's own configuration.
- **Search** of terminal output reads history on demand; no index, no recording.
- **Migration reads; it does not touch what is running, with one exception.** Scanning and listing only read. Nothing edits the user's dotfiles or writes under an agent's own folder; snippets are printed for the user to add. Per-OS process inspection lives in `daemon/src/migrate/shells.ts` only, with parsing as pure functions under test. The single exception is stop-and-resume (`aubergine move --stop` and the panel's button), which may send one termination request (SIGTERM) to an agent process. It must stay limited to the exact process IDs the user selected, verify immediately before that each still is the same Claude Code process (start time from its record against the process table), refuse agents that are not idle unless forced, ask for confirmation, never send a second or stronger signal, and start nothing on the canvas if the process does not exit. Test it only against stand-in processes the test starts itself.
- **Outside terminals.** The panel and the CLI both go through `Outside` in `daemon/src/migrate/outside.ts` and its `/api` routes; do not add a second path. Those routes are cookie-only and must never accept a session token. A request carries only a terminal name and a process ID from the listing; the daemon re-derives the folder, conversation, idle state and process identity before acting, and never uses a folder, command or conversation ID sent by a client.
- **Agent launch line.** Built only by `claudeLaunchLine` from `agents.claudeCommand` in settings plus quoted arguments. The command is trusted configuration typed into the user's shell; it and the agent arguments must never come from anything a session token can send. Conversation IDs must pass `ConversationId` before they are stored or typed.
- **Agent process records** (`~/.claude/sessions`) are an internal detail of the agent: read them only in `daemon/src/migrate/claude-sessions.ts`, validate with zod, and always have a path for "not readable".
- **Showing a session** never changes state and never opens a browser from `--no-attach`, the shell snippet or `import`. Addresses never carry the access token.
- **The shell snippet must always fall through to a normal shell.** Any change to it needs the tests for server up, stopped, hanging and command missing to pass. `here --from-shell-hook` is quiet and reports failure only by exit code.
- **Generated files that start Node** (the shell snippet, the login service, agent settings) take the path from `stableNodePath()` in `daemon/src/node-path.ts`, never `process.execPath`, so they survive a Node upgrade.
- **The installer changes two things only**: the install folder (`~/.aubergine`, or `AUBERGINE_HOME`) and one link named `aubergine`. It never uses `sudo`, never writes a shell startup file, never installs Node, pnpm or tmux, never touches the data folder, and replaces nothing at the link's place that is not its own link. It stays POSIX `sh`, with its whole body in a function called on the last line. Every check runs before anything is changed.
- **Where this copy is, is `packageRoot()`** (`daemon/src/package-root.ts`): the nearest folder above the module with `bin/aubergine.mjs`. Every path to the copy's own files (the web app, templates, the library, the demo, the tmux configuration, the command) is worked out from it, never from a module's depth, because the npm package runs compiled files at another depth. `entryArguments` (and `bin/aubergine.mjs`) run `dist/<name>.mjs` where it exists, else the source through tsx.

It holds `.installed-from-npm`, so `update` and `uninstall` leave the code and the command to npm and say the npm command. Only `.github/workflows/publish.yml` publishes it, on a pushed tag `v<version>` that matches `daemon/package.json`, through npm's trusted publishing (no token is stored). Nothing else publishes it, and the build script never does.

Each platform is built on a runner of its own kind and tried before anything is pushed; the image pushed is the one tried. Run by hand it pushes nothing. Nothing else pushes the image.

No other published port, no `EXPOSE` of Aubergine's port, no `0.0.0.0`, no `--host`, nothing privileged, no Docker socket, and only named volumes on the `aubergine` service: no folder of the host.
- **The image is built from the checkout by `scripts/npm-package.mjs`**, and installed from the file it packed; never from the registry by name, never by a second build path.
- **The entrypoint fills in only what is missing.** `~/.zshrc` (empty, so that zsh asks no first-run question) and `config.json` with `AUBERGINE_ADDRESS`, each only where none exists, never replaced; an address that holds anything an origin cannot is refused. It does nothing else and ends with `exec "$@"`. It is the operator's own setting at start, not a route.

- **The container files were run once**, on 2026-11-22, on an Apple-silicon Mac with Docker in Colima (linux/arm64), under `https://aubergine.localhost` with the web server's own certificate; every document about them says that and what was not tried (a public certificate, a cloud machine, linux/amd64 beyond the release workflow's trial run, BuildKit, a phone, an agent inside). Say no more than was run. `daemon/src/container-files.test.ts` reads them as text and guards the rules above; keep it passing.
- **`uninstall` removes only what the installer made**: links that point at this copy, and the copy's folder only when `.installed-by-installer` is beside it. Never a checkout someone made, never the data folder, never a session.

Never edit a file under `site/`. How it is made, what a page may say and how it looks are in `docs/site.md`: read it before changing the site.

A stale or missing translation is shown in English until it is made again; the check lists them. Commands, addresses and names are never translated. The app itself is in English, and a translated page says so, and that a machine translated it.

What it does by itself for an agent is built for Claude Code; any other agent can say the same through the `aubergine` commands when its own instructions tell it to. No page blurs the two, imitates another company's product, or says more about one than that it is a command-line agent a person installs and signs in to.

Only the pages under `/compare/` do this (`docs/site.md`), and a fact about a tool is one string, used by its page and by the page of all of them.

### The look

- **The look is in three places and nowhere else.** The owner's own stylesheet is not part of the system: it is loaded after it, and nothing of the system is written there. `web/src/tokens.css` has every size, weight, colour, space, corner, control height and layer, and `web/src/themes.css`, part of the tokens, the colours of every theme beyond Light and Dark. `web/src/ui/ui.css` has what a control, a chip, a tab, a menu and a card look like (`web/src/ui/index.tsx` has the same as components). `docs/design.md` says when to use which. A screen's rule in `styles.css` says where things are, never what a control looks like.
- **No number where a token belongs.** A font size, a weight, a corner, a colour, a layer or a control's height written as a number, and a space off the grid of four, fail `web/src/ui/design.test.ts`. A new one is a change to the tokens and to `docs/design.md`, with its reason. The exceptions are a terminal's own text and the colours a person picks.
- **Four sizes, two heights.** Text is 12, 13, 15 or 20px. A button, a field and a select are 32px, or 28px in the side panel's lists, the bar over the canvas and a terminal's title. The one exception is New terminal at the top of the list, 40px (`--control-large`). A name too long for its room is cut off, with no "…". ### Canvas behaviour

- A terminal takes input at any zoom at which it is drawn live, and only while it has focus. One click focuses it and moves nothing; only a node too small to read (below `READABLE_ZOOM`) zooms in first. An unfocused terminal is covered by a shield: the first click focuses it.
- On a canvas that is not at 100%, the pointer is told to the terminal as it would be at 100% (`correctMouse` in `web/src/scaled-mouse.ts`); without that, selections land in the wrong cells. The same module evens out the wheel: one report for every `LINES_PER_REPORT` lines of movement, at most once a frame, and `tmux.conf` moves the scroll-back view by that many lines per report. Change the two together.
- A terminal's note is beside the node, outside its rectangle, open unless closed in this browser (`note-open.ts`). Being there never takes the keyboard; being asked for does. A click in it is the note's: `onNodeClick` gives the terminal the keyboard for no click inside `.note-panel`, a control or a link.
- **The summary keeps its height between read and changed.** The box grows with its text (`NotePanel`). Beside a terminal it is typed into as it stands, four lines at least, and stops at a share of the note and scrolls there. In the details it is read until it is pressed, as tall as its words (one quiet line while there is none), and the box that changes it is no shorter than what was read. Otherwise pressing it or leaving it moves what is under it.
- **A note moves only its own log.** Beside a terminal the newest entry is kept in view by scrolling the log's box (`.note-log`), never with `scrollIntoView`, which also moves what the note stands in. In the details the log is part of the one column that is read from its top: nothing there moves by itself, and only an entry written there is brought into view.
- **A share of the note is of the note.** Beside a terminal the note is a size container and the summary's cap is in its units (`cqh`): a percentage would be of the part the summary stands in, whose height comes from the summary.
- **Where the log is added to follows the log.** One row (`.note-add-row`) under the last entry: at the foot of the note beside a terminal; in the details directly under the entries, and kept at the foot of the details while the log is in view.
- **The log is told by day.** `logDays` in `web/src/note-log.ts`, a pure function of the entries and the time: a quiet heading for each day (Today, Yesterday, else the date, with the year when it is another), and under it the entries with who and the time of day. The oldest day first; nothing reorders entries.
- A color is a named one or `#rrggbb`. `colorClass` and `colorStyle` in `web/src/color.ts` are the only place a color becomes a class or a style.
- Terminal bodies never drag or pan the canvas. The wheel belongs to a terminal only while it has focus; anywhere else it zooms the canvas.
- **Commands.** Everything a button, a key or the palette does is a command in `web/src/commands.ts`, implemented once. A new action is a new command there and a new name in `COMMAND_IDS` in `shared/src/shortcuts.ts`; a button calls `runCommand`. Do not handle a key anywhere else: `web/src/shortcuts.ts` is the only key listener for commands.
- **Two layers of keys.** A chord works inside a focused terminal only if `belongsToTerminal` says no program there can need it: it includes ⌘ on macOS, or is Ctrl+Shift with a key elsewhere. Everything else (plain keys, Ctrl+key, Alt/Option+key) works only while no terminal, text field, menu or list has the keyboard, whatever the settings file says. Do not weaken that function; its tests list the shell keys that must get through.
- **Keys are data.** Defaults per platform are in `shared/src/shortcuts.ts`; `resolveShortcuts` applies `shortcuts` (and `shortcutsInAppWindow`) from the settings and returns problems, which the sheet and the server log both show. A wrong entry is reported and skipped, never a reason to drop the file. The sheet, the palette and tooltips read keys from the resolved bindings; never write a key into the interface by hand.
- **Do not claim a chord is safe without measuring it.** `docs/keys.md` records what was measured and how; the list of chords browsers keep (`keptByBrowser`) is documented behaviour until someone runs the key tester. Automation cannot measure this: it delivers chords a real key press never would.
- **The browser's tab keys.** Ctrl+Tab and Ctrl+Shift+Tab are the one exception in `belongsToTerminal`: terminal programs do not receive them as distinct keys, so they may switch canvas from inside a terminal. Plain Tab and Shift+Tab in a focused terminal always go to the program. Chords a browser keeps are bound, not refused; whether they arrive is the browser's decision. Function keys work from a text field or a list, never from a terminal; `F6` reaches every group of controls.
- **The side panel is a shell.** Its head is one `Switcher` whose menu lists every registered section, with what it shows and its count; the one that is chosen has all of the panel's height. It knows nothing about what they show. Do not put tabs back in its head. A section whose count is of things waiting on the owner says `urgent`: its count is then in the color of waiting as text, and the head carries one small dot while another section shows. Do not stack sections again: five lists in slices of one column was the thing people could not use. A section whose count is of things waiting on the owner says `urgent`.
- **The bar over the canvas has no bare signs and never runs off the edge.** "Go to…", the view, and what needs the owner at the right; anything made less often than a plain terminal goes in the menu beside "New terminal" at the top of the list, with a line saying what it is. Under `NARROW_CANVAS` the terminals that are not on the canvas are in its "More" menu. A new screen gets a word, not a symbol. It wraps before it overflows; a browser test checks both. A new panel feature is a module in `web/src/panel/sections/` that calls `registerSection`; do not add content to `SidePanel.tsx` or import a section from anywhere else. The detail drawer belongs to the shell: a section declares a drawer by kind and opens it with `openDrawer`; it never draws its own.
- **A new filter is a registered predicate.** `registerFilter` in `web/src/list-filters.ts`, a pure test of one row. Filters combine with AND. Do not filter rows anywhere else, and do not special-case a filter in the component.
- **The list is data first.** Rows, state, filtering, grouping, sorting and windowing are pure functions in `terminal-rows.ts` with tests; the component only draws their result. The list and the commands that move through it both ask `listModel`, so they cannot disagree. Only rows in view are drawn; a change to one session must rebuild one row (there is a test with 1,000 sessions; keep it passing).
- **Row state is derived, never stored.** `rowState` works it out from `status`, `attention` and `state`. Do not add a stored field for "read" or "processing".
- **Times are throttled.** `lastInputAt` and `lastOutputAt` are recorded at most once per `TIMES_INTERVAL_MS` per session, never per keystroke or per line of output. What a terminal sends by itself (`isTerminalReply` in `daemon/src/terminal-replies.ts`) is not input. A test counts the events for a line typed key by key.
- **One implementation each** for notes (`NotePanel`, embedded in the drawer) and for editing tags (`TagDialog`); the list and the node both use them.
- **Tab follows the list.** `select.next` and `select.previous` walk `listModel(...).order`; the default scope is the canvas being looked at so Tab does not change canvas by surprise. A button pressed with the mouse gives the keyboard back to the canvas (also inside the list), so plain keys keep working after a click.
- **Selected is not focused.** `selected` in the store is the terminal that commands act on while none has the keyboard; focusing selects, leaving keeps the selection. Keys typed between asking for a terminal and its having the keyboard are never canvas keys (`settleUntil`).
- A glide that stays at 100% must pan in a straight line (`interpolate: 'linear'`): the default path zooms out on the way and a focused terminal loses the keyboard.
- Closing a node parks its session; it does not end the shell. Ending a shell for good always asks first.
- A node keeps a live terminal (and its WebSocket) only while it is on screen and readable; otherwise it shows a snapshot or nothing. The decision is `nodeMode` in `web/src/culling.ts`.
- Going to a node (`goToNode`) must not depend on animation frames, which stop in a tab that is not showing.
- Only the canvas being looked at mounts terminals or fetches snapshots. The address is `/c/<id>`; pan and zoom are kept per canvas per browser. A request to show a session (`show` in the store) is used once and then cleared. `Viewers` decides which tab is asked to show a session.

### Tests

- Tests that type into a new session must wait for the shell's prompt first (`createReady` / `shellReady` in the daemon tests): a shell discards what is typed while it is starting.
- Tests await `sessions.refresh()`; never leave one running past teardown.
- **Test runs must not share anything on the machine.** Every test file that starts tmux takes its socket name from `testSocketName()` in `daemon/src/test-support.ts` (unique per run) and tears down with `destroyTmuxServer`, which ends only that server. Ports are 0 or per run, data folders are temporary and per run, and the browser test's port, data folder, socket and results folder come from the run ID in `playwright.config.ts`. Two checkouts must be able to run `pnpm check` at the same time.
- **Installer and command tests never touch the real machine**: a temporary `HOME`, a `PATH` made of links to individual tools (never a real bin folder, which may contain `brew`), a test port and a test tmux socket. Tests that keep the machine busy (`*.installtest.ts`, `*.busytest.ts`) run as their own step, not beside the daemon tests.
- Fixtures use made-up values: no process IDs, paths or names copied from a real machine.
- The Playwright test includes a pass made with the keyboard only; keep it mouse-free.
- Runs that stall for minutes inside a short wait mean the machine slept; check `pmset -g log` before changing a test.
- Playwright actions have a 15 s limit; wait for a node to be in view before clicking near it, since a click interrupts the glide.
- Shell-integration tests use a stand-in `ZDOTDIR`; never assert against, or write to, the developer's own startup files. The same goes for the shell snippet tests.

## Checks

```
pnpm check
```

runs, in order: type checking, lint, shellcheck on `install.sh` where it is installed (it skips with a note where it is not), unit tests (Vitest; the tmux runtime and server tests use a real tmux on test sockets) and the Playwright smoke test (builds the web app and starts a daemon with its own data folder, port and tmux socket). A task is not done until it passes.

Single steps: `pnpm typecheck`, `pnpm lint`, `pnpm test`, `pnpm e2e`, `pnpm generate` (and `pnpm generate --check`, which `pnpm check` runs first).

`pnpm start` serves the built web app and opens the browser signed in; `pnpm serve` is the same without the browser. `pnpm dev` starts the daemon (port 4600, restarts on change) and the Vite dev server (port 5173, proxies `/api`, `/auth` and `/ws` to the daemon).

`pnpm load-canvas` fills three throwaway canvases with 90 sessions between them for judging scale by hand. It is not part of `pnpm check`.

Environment variables, all optional: `AUBERGINE_PORT`, `AUBERGINE_DATA_DIR`, `AUBERGINE_TMUX_SOCKET`, `AUBERGINE_TMUX_BIN`, `AUBERGINE_DEV_ORIGIN`. Use a separate data folder and socket for experiments so they do not touch real sessions.
